# 知识卡规范

## 卡片编号

格式为 `<系统>-K<四位数字>`，例如 `TRU-K0001`。系统前缀只允许：

- `STC`
- `EGR`
- `TRU`
- `FLD`
- `MCK`

编号表示来源系统，不表示跨书裁决结果。

每张卡另设 `concept_key`，表示该著作内部的稳定知识概念。同一 `work_id` 下不得出现重复 `concept_key`；不同译本或文件支持同一观点时，向同一张卡追加证据，不复制卡片。

## 内容层级

- `[作者主张]`：原书确实表达的观点，必须由书籍证据支持。
- `[操作化整理]`：把作者观点转换成生成、诊断或修改动作。
- `[AI短片适配]`：针对用户生产方式的推断。
- `[用户笔记]`：用户自己的理解。
- `[外部补充]`：原书之外的资料。

不得删除标签后把后四类写成作者主张。

## 必填能力

每张知识卡必须明确：

- 解决的问题；
- 所需输入；
- 生成问题；
- 诊断标准；
- 修改方法；
- 适用条件；
- 禁用条件；
- 常见误用；
- AI短片适配；
- 验证记录。

字段可以为空数组，但必须显式存在，以便区分“已判断为空”和“尚未处理”。

## 跨书关系

G60 前只允许：

```json
{
  "target_card_id": "EGR-K0001",
  "relation_type": "related",
  "governance": "link_only",
  "note": "只记录关联，不裁决或融合"
}
```

不得使用 `overrides`、`proves`、`merged` 等越权关系。

## 卡片状态

- `draft`：允许存在 `ocr_unverified`，不得进入运行 Skill。
- `reviewed`：证据和操作化已经复核。
- `approved`：可以进入后续集成目标。
- `revalidation_required`：来源文件变化或定位失效。

`reviewed` 和 `approved` 卡片必须至少包含一条 `text_layer` 或 `ocr_verified` 证据。
